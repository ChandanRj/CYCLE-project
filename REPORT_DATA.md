### 0.1 Discrepancies and caveats found while compiling (read before drafting)

1. **"debug_n=1024 vs paper's 10,373" is not the right comparison.** `data.debug_n` caps the number of **training mentions**. The file has 1,764 training mentions, and the paper trains on all 1,764 (paper Table 1). So the debug runs use 1,024 of 1,764 training mentions (58%). The value 10,373 is the number of **entities per year**. Every evaluation in this project uses the full 10,373-entity pool and all 48,215 test mentions. Validation is also capped: `valid_n=256` (or 64 in two early runs) of the 43,327 validation mentions.
2. **Validation size.** Paper Table 1 lists 42,096 validation samples. The files contain 43,327 lines: 42,096 with `category: "shared"` and 1,231 with `category: "new_entities"`. The paper's figure equals the "shared" count.
3. **Entity count.** Paper Table 1 lists 136,227 entities for GCL-TempEL. Each yearly pool in the data files has 10,373 entities, and the code uses 10,373.
4. **The new and continual test/validation files are byte-identical** (md5 `89472cd7…` for test, `dfad4ea4…` for validation, year 2019). Only the **training** files differ: "new" has 1,764 mentions of 373 distinct entities, all `category: "new_entities"`; "continual" has 1,764 mentions of 1,168 distinct entities, all `category: "shared"`. The "new" vs "continual" difference in results therefore comes from the training set alone.
5. **Epochs.** The paper trains for **1 epoch** on GCL-TempEL (Section 6.2). The runs here use up to 12 epochs with early stopping (patience 3) on in-batch validation accuracy.
6. **Feature dimension.** `data/README.md` (upstream) says the feature matrices are 10,373 × 2,914. The processed graphs (`data/processed/graphs/2019.npz`, `X_shape`) are **10,373 × 2,929**, and PROGRESS.md uses 2,929. The value 2,914 matches the `samples2015` HeCo features used by `configs/baseline.yaml`.
7. **Paper internal inconsistency.** The paper text gives the new-entity @1 boost at a 3-year gap as 15.25%, while its Table 2 gives 15.28.
8. **Gap definition.** The paper defines gap 0 as the same year and gap 3 as "trained in 2019 and tested in 2022". It trains a model each year from 2019 to 2022 and tests "across other years", with forward and backward settings. The paper does not say explicitly whether its gap-1 and gap-2 cells average several train/test pairs. All runs here train on 2019 only, so gap *k* means test year 2019 + *k*.
9. **`outputs/` is git-ignored.** Only the `results/` copies (candidate-mode and mining/weighting runs) are committed. The gold_mention runs (`new_2019_paper_seed52313{,_v2}`, `new_2019_paper_extranneg_seed52313`, `continual_2019_paper_extranneg_seed52313`) and the early runs exist only under `outputs/` on this machine.
10. **fusion.mode in older configs.** Runs made before commit `000cb57` have no `fusion.mode` key in `config_used.json` (shown as "—" in Section 11). The code default is `gold_mention` (`cfg.fusion.get("mode", "gold_mention")`, `src/cycle/train.py:267`).

## 1. PROJECT SUMMARY

### 1.1 One-paragraph summary

This project re-implements the model components of CYCLE (Cross-Year Contrastive Learning in Entity-Linking; Zhang, Cao, Zaporojets and Groth, CIKM 2024) on top of the authors' released training and evaluation scaffold. It then tests the method on the GCL-TempEL temporal entity-linking benchmark. The implementation covers:

- a BLINK-style bi-encoder (Eq. 1–5);
- a per-year graph module with GAT-style attention aggregation over a relation graph and a kNN feature graph, and a shared ELU MLP (Eq. 6–9);
- cross-year positive and negative sampling from relation-edge changes between consecutive years (Eq. 10–12);
- two cross-view InfoNCE losses, L_f and L_r (Eq. 13–14);
- the joint objective L = a·L_e + b·L_f + c·L_r (Eq. 15);
- a HeCo baseline graph module.

All experiments train on **year 2019** with seed 52313, plus seeds 2 and 3 for the multi-seed batch. They use `debug_n=1024` training mentions (of 1,764) and `valid_n=256` validation mentions (64 in the two earliest runs). Evaluation uses the full pool of 10,373 entities against all 48,215 test mentions for each test year 2019, 2020, 2021 and 2022 (gaps 0–3). Most runs use the **new-entities** set, and one run uses the **continual-entities** set. The graph data covers ten yearly snapshots, 2013–2022. One early run trained on 2015 and tested on 2015–2018. The work produced five main findings:

1. Eq. 11 cross-year negatives are structurally empty on this dataset.
2. Entities that do not exist in the training-year graph bias candidate-mode evaluation.
3. The paper's dot-product graph embeddings collapse.
4. Learned loss weighting gives no gain.
5. Checkpoint selection, not the method, explains most R@1 differences between runs.

### 2.2 Settled design decisions (PROGRESS.md §3, verbatim)

- L_f denominator is restricted to P_i^r ∪ N_i^r (Eq. 13). The L_r denominator covers all n nodes (Eq. 14).
- L_r positives are the kNN feature-graph neighbours. L_f positives are the newly added cross-year relation edges.
- InfoNCE is sum-then-log: `-(logsumexp(pos) - logsumexp(denom))` per anchor.
- Zero-positive guard: `anchor.sum() * 0`, which keeps the grad_fn.
- OOM fixes: `_aggregate_and_project` is chunked (`agg_chunk=1024`) with gradient checkpointing and split-weight attention. `_infonce_r` is chunked row-wise. `_infonce_f` gathers `target[pos_idx]` directly. Training now peaks at about 2.5 GiB.

## 4. FINDING 1 — Eq. 11 cross-year negatives are always zero

### 4.1 Statement (PROGRESS.md §4 finding 1, verbatim)

> **The Eq. 11 cross-year negatives are always 0 on GCL-TempEL.** This comes from the data, not a bug. Each year has 10373 nodes: 10000 shared entities plus 373 year-specific ones. The 5007 edges among the shared entities are identical in every year, and every added or removed edge touches a year-specific entity. As a result, L_f = 0 exactly, with zero gradient. From 2020→21 onward there are no positives either. `scripts/diag_negatives.py` reproduces this. Deviation: `graph.relation_extra_negatives=K` adds sampled negatives to L_f.

Mechanism: with N_i^r empty, the Eq. 13 denominator P_i^r ∪ N_i^r equals the numerator set P_i^r. Then log-sum-exp(pos) − log-sum-exp(denom) = 0 for every anchor, so L_f = 0 exactly and has no gradient.

## 5. FINDING 2 — Unmapped-entity test-time bias (candidate mode)

### 5.1 Statement (PROGRESS.md §4 finding 5, verbatim)

In test 2020–22, 373/10373 pool entities have no 2019-graph node, and `enhance_pool` gave them a zero adjustment, which never occurs in training. ## 6. FINDING 3 — Graph-embedding collapse

### 6.1 Statement (PROGRESS.md §4 finding 6, verbatim)

> **The paper's dot-product graph embeddings collapse, and neither cosine similarity nor hard-negative mining raises R@1.** Setting: candidate mode, extra negatives=8, train 2019, 3 seeds per arm (tables in §5). Four points:
> 1. *Collapse is present at initialization.* X is a row-normalized bag-of-words over 2929 dims, so the input term of the first layer is tiny next to its bias (|W1 x| ≈ 0.014 vs |b1| ≈ 0.083). Every node therefore maps to nearly the same vector: pairwise cosine 0.99985 (z_r) and 0.99994 (z_f), with 99.98% of the energy in the top singular direction.
> 2. *The dot-product loss cannot escape it, and "cheats" through vector length.* After training, the dot arm is still at pairwise cosine ≥ 0.9998 in every seed. Entities differ only in norm (about 4–5, up from 0.57 at init). L_f drops from chance (2.02) to about 0.5–1.0 because positives are made longer than negatives (|z_r| 4.97 vs 4.30 for seed 52313), not because they point elsewhere: both have cosine ≈ 1.000 with the anchor. The bias still dominates (|b1| 0.67–0.78 vs |W1 x| ≈ 0.055). In candidate mode this makes the graph adjustment close to a constant shift, so it barely changes rankings.
> 3. *Cosine similarity resolves the collapse and stabilizes seeds, but does not raise mean R@1.* Pairwise cosine drops to 0.44–0.55 (z_r) and 0.17–0.26 (z_f), top-direction share to 0.77–0.84, and L_f separates by direction (positives cos 0.96–0.98, negatives −0.61 to −0.73). Seed-to-seed R@1 range shrinks from 6.6 points (dot) to 1.3 points, but the mean (0.277) is within noise of dot's best seeds (0.281, 0.277).
> 4. *Hard-negative mining (on top of cosine) has a measurable effect on the loss and none on R@1.* L_f stays at 1.5–1.85 instead of falling to about 0.9–1.0 with random negatives, since the negatives are now the hardest ones (negative cosine ≈ 0 instead of −0.6 to −0.7). R@1 per seed is 0.299 / 0.275 / 0.224, the same pattern and spread as dot. A likely reason: L_f only touches 12 of the 10373 anchor nodes on the 2019 graph (16 positive pairs), so how its negatives are picked barely reaches the rest of the model.
>
> The between-arm R@1 comparisons in this finding are further qualified by finding 7; the collapse metrics are not.

## 7. FINDING 4 — Learned loss weighting (null result) and FINDING 5 — checkpoint-selection dominance

### 7.1 Finding 4: setup (PROGRESS.md §4 finding 7, verbatim)

> This replaces the fixed Eq. 15 weights with Kendall et al. (2018) uncertainty weights, L = Σ_i L_i/(2σ_i²) + log σ_i (`loss.weighting=learned`, `weighting_lr=0.01`). The effective weights start at exactly a = b = c = 1. Arm: random + cosine, extra negatives=8, candidate mode, 3 seeds, compared with the existing random + cosine seeds as the fixed-weight arm. Regression runs (run by hand, not committed as tests) were bit-exact: the fixed path reproduces the committed `extranneg_cos_seed52313` log, and `weighting_lr=0` reproduces the fixed run, logs and all 276 checkpoint tensors included.

Implementation: `src/cycle/models/loss_weighting.py` (`UncertaintyWeighting`). log σ_i = s0_i + δ_i, with s0_i = −½·log(2w_i) fixed and δ_i learned from 0, so the effective weight is w_i·exp(−2δ_i). Its parameter group is excluded from gradient clipping. The loss is assembled at `train.py:370–378`. Commit `a6ef8e6`.

### 7.2 Finding 4: learned weights follow loss size, not noise (PROGRESS.md, verbatim; epochs ≥ 2, 3 seeds)

| Term | Trajectory (start 1.0) | End weight | Mean loss | 1/(2·loss) | Step-to-step CV |
|---|---|---|---|---|---|
| L_e | dips to 0.65, then rises every epoch | 0.67–0.74 | 0.50 | 0.9–1.0 | 0.59 (noisiest) |
| L_f | down, flat from epoch 1 | 0.52–0.54 | 0.94 | 0.53 (w·2L = 0.97–0.99) | 0.12 |
| L_r | down every epoch | 0.09–0.12 | 7.45 | 0.067 | 0.01 (least noisy) |

> The weight order e > f > r matches the loss-size order and is the reverse of the noise order. L_f sits at its magnitude equilibrium; it is not weighted down further for its noise or for having only 12 anchors. L_e and L_r are still moving toward 1/(2L) when the learning rate decays to 0. This is expected: the objective's stationary point is σ_i² = E[L_i], whatever the variance. So the mechanism reacts to raw loss size and does not compensate for L_f's sparsity.

### 9.3 Notes for interpreting the comparison

- The paper trains for 1 epoch on all 1,764 training mentions. These runs train for up to 12 epochs with early stopping on 1,024 mentions, selected on 256 validation mentions (Section 0.1).
- New entities: the Δ columns in 9.1 give, per gap, my R@1 minus the paper's CYCLE R@1. Positive values mean higher than the paper. By Finding 5, differences *between my runs* mostly follow the chosen epoch.
- Continual entities: the single continual run (0.3840–0.3879) is above the paper's CYCLE R@1 (0.286–0.301). PROGRESS.md finding 4 attributes the continual training loss (loss_e ≈ 0.01) to memorisation.
- The paper reports that CYCLE's advantage over BLINK grows with the gap. Here R@1 is flat across gaps: see the "max−min" column of Section 8.1. The only exceptions are the two BROKEN candidate-mode evaluations, an artefact explained by Finding 2. The paper's own CYCLE R@1 rows change by 0.015 (continual, 0.286→0.301) and 0.038 (new, 0.184→0.222) from gap 0 to gap 3.
- *Interpretation, not stated in PROGRESS.md:* the paper's BLINK row is the closest analogue of the text-only control (graph and fusion off). The control scores 0.2459–0.2495 against the paper's BLINK new-entity scores of 0.132–0.142.

## 10. LIMITATIONS (as documented in PROGRESS.md, plus facts needed to state them)

1. **Single seed for most comparisons.** All §5 runs (text-only control, paper-strict v1/v2, extra negatives, candidate modes, continual) use seed 52313 only. Only the mining/weighting batch has 3 seeds (52313, 2, 3). PROGRESS.md §5 (verbatim): "The extra-negatives gain over v2 is +0.3 points from a single seed, so it is not significant." PROGRESS.md §6: "Multiple seeds would show whether the small differences are real."
2. **Debug scale.** Training uses `debug_n=1024` of 1,764 training mentions and `valid_n=256` of 43,327 validation mentions (Section 0.1 item 1). Testing is full scale: 10,373 entities and 48,215 mentions per year. PROGRESS.md §6 (verbatim): "Full-scale runs (no `debug_n`) and other train years have not been run. Note that train years 2021 and 2022 give L_f no signal."
3. **Checkpoint-selection noise** (Finding 5). r(chosen epoch, R@1) = 0.97 over n = 12, but r(best validation accuracy, R@1) = 0.41. One validation mention equals 0.39 accuracy points, and ties keep the earliest epoch. Every 1–2 point R@1 comparison between runs is unresolved. The controlled fixed-epoch test was scoped but not run, because checkpoint cleanup (`train.py:436–440`) keeps only the best and last epochs.
4. **Flat recall across test years.** PROGRESS.md §5 (verbatim): "R@1 is averaged over test years 2019–2022 (the four years are within 0.6 points of each other in every run)." **PROGRESS.md does not document an explanation of this pattern.** Documented facts that bear on it:
   - PROGRESS finding 2: in gold_mention mode the graph is not applied at test time, so the test year's graph cannot affect scores. Only the text encoders act.
   - Finding 2 (unmapped): before the fix, candidate mode was the one setting that produced a 2019 → 2020+ drop, and that drop was an artefact.
   - Data facts computed for this document: the pools of 2019 and each later year share 10,000 of 10,373 entities. 46,765 of 48,215 test mentions per year are `category: "shared"`. The test mentions are entirely different each year (0 shared `mention_id`s with 2019), and entity descriptions do drift (only 4,156 / 2,382 / 1,604 of the 10,000 common entities keep identical text in 2020 / 2021 / 2022).

   Any causal explanation of the flatness beyond these facts would be new analysis, not a documented result.
5. **Continual memorisation.** loss_e reaches about 0.01 (Section 7b).
6. **Eq. 11 is structurally empty** on GCL-TempEL, so the paper-strict L_f is identically zero. The extra-negatives variant is a deviation, and L_f touches only 12 of 10,373 anchors for train year 2019.
7. **Test-time fusion mechanism unspecified by the paper.** Both fusion modes, and the unmapped-entity rule, are this project's choices (D2, D11).
